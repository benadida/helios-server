Voting reads were creating discarded Django sessions, while two synchronous HTTP slots and repeated remote checks amplified hosted latency. This change makes ballot/receipt/status JSON adapters stateless, authenticates private status before database access, uses request-local casting context, retains the final fresh membership check, and reduces repeat binding/user/voter reads. HTTP runs with two gthread workers of four threads; service connections are bounded, thread-owned and reject cookies without automatic POST retries.

Verification jobs remain durable and atomic with acceptance. PostgreSQL sends an empty wake hint after commit; dedicated listeners retain polling and reconnection fallback. Cloudflare placement is constrained to ENAM, with read-only post-deploy location/database diagnostics. The existing keep-alive/recovery routing name is preserved.

Validation: 314 Django/PostgreSQL tests passed, including concurrent registration, rejected proofs, role changes, rollback/recovery, post-commit notifications, and actual loopback connection/cookie isolation. Worker types/check and frontend real crypto/UI integration passed. Isolated three-position profile: acceptance 37→28 commands, pending status 8→3, ballot read 6→2, verified status 7→3; callbacks 3→2. These are local command counts, not production latency guarantees. Budget: up to 13 persistent PostgreSQL connections across 8 HTTP threads, 2 verifier ORM connections, 2 listeners and 1 sender (plus transient maintenance/deploy connections).
